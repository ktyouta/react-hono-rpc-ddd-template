# Frontend Review Skill

## Overview

フロントエンド実装後に、コンポーネント設計の違反パターンをチェックする。

---

## Check Instructions

### フォルダ・ファイル構成
- `features/[機能名]/` 単位でフォルダが切られているか（kebab-case）
- `components/` 配下がフラットになっているか（サブフォルダを作っていないか）
- `api/` 内が操作単位でファイル分割されているか（`get-xxx.ts`, `create-xxx.ts` 等）
- `api/query-key.ts` が存在し、クエリキーがここに集約されているか
- Container コンポーネントのファイル名に `-container.tsx` サフィックスがついているか
- `hooks/` 内が責務単位でファイル分割されているか（`use-[機能名]-[操作].ts`）
- フォーム専用 hook が `use-[機能名].form.ts` で定義されているか（フォームがある場合）

### Presentational コンポーネントの純粋性
- `useState` / `useReducer` などの state 管理が含まれていないか
- `onClick` などのイベントハンドラが直接定義されていないか（props 経由の受け取りは可）
- データフェッチ・副作用（`useEffect`）が含まれていないか

### 共通コンポーネントの利用
- ボタン・入力フィールド等、既存の共通コンポーネントが存在する場合はそれを使用しているか（インラインでスタイルを書いていないか）
- 実装前に `src/components/` 等の共通コンポーネントを確認しているか
- アイコンには `react-icons` を使用する（例: `react-icons/lu`, `react-icons/io5` 等）
  - 新しいサブモジュール（`lu` 等）を初めて import した場合、Vite の事前バンドルキャッシュ更新のため dev server の再起動が必要になることがある

### カードのコンテンツ密度
- フルワイドカード（`rounded-3xl border-2 bg-white shadow-*` 相当のスタイル）に対してコンテンツが1行・1フィールドのみになっていないか
  - アンチパターン: 1行程度のテキストにフルワイドカードを使う（横幅に対して中身が空疎になる）
  - 正しいパターン: 1行程度のデータはインライン表示・コンパクトなバッジ・テキスト行で表現する。カードは複数行のコンテンツがあるときに使う

### 背景色の上書き確認
- 新規コンポーネントの親・祖先（レイアウトコンポーネント含む）に `bg-white` / `bg-*` が設定されており、
  子で設定した背景色が無効化されていないか確認する
  - アンチパターン: 親に `bg-white` があるのに子で `bg-amber-100` を設定しても見た目が変わらない
  - 確認方法: 変更ファイルだけでなく、それを import・wrap している親コンポーネントのファイルも Read する

### コーディング規約
- `if` 文が1行でも中括弧 `{ }` を省略していないか。また処理が1行でも `{ return; }` のように同一行に収めず、改行して記述されているか
- `useState` / `useRef` / `useMemo` / カスタム hooks の返り値などの state 系変数について、comments-review の基準（名前から意図が明確かつ定義直後にしか使わない場合を除きコメントを付ける）に沿っているか
  - hooks 返り値から派生した変数（例: `const x = query.data.data`、`const map = new Map(query.data...)` 等）も同基準の対象に含める
- state 系変数にコメントを付ける場合はインライン形式（`// 説明`）で記述する。JSDoc 形式（`/** 説明 */`）は関数・メソッドのドキュメント専用であり、変数コメントに使用しない
- 関数・メソッドに JSDoc コメントがあるか（`/** 説明 */` の多行形式。パラメータがある場合は `@param`、戻り値がある場合は `@returns` を含める）
  - エクスポートされていないプライベートヘルパー関数（例: ファイル内の変換ユーティリティ）も対象に含める
- コメントに実装詳細が含まれていないか
  - 実装詳細の例: 「どこから取得するか」「どの HTTP メソッドを呼ぶか（DELETE・POST 等）」「どのフック名を使うか」
  - 良い例: `// アイテム削除`
  - 悪い例: `// アイテム削除（DELETE API）`
- props 型が `type PropsType = Pick<XxxType, '...'>` 形式になっているか
- マジックナンバーが直接記述されていないか（名前付き定数に切り出すこと。定数値は意図が読み取れる形で書く）
- 子コンポーネントへ `props` として渡すコールバック関数は `useCallback` でラップされているか
  - アンチパターン: `function handleDelete(id) { ... }` を `onDelete` として渡す
  - 正しいパターン: `const handleDelete = useCallback((id) => { ... }, [deps])` とする
- テキストサイズが以下の使い分け基準に沿っているか
  - `text-sm`（14px）: 意図的に目立たせない副次的アクションのみ（例: 「やり直す」ボタン）
  - `text-base`（16px）: ユーザーが能動的に読む・操作するすべての要素（ボタン・ラベル・入力テキスト・説明文・バリデーションエラーメッセージ等）
  - `text-xl` 以上: 見出し・ページの顔・主役ラベル

---

## Procedure

1. 変更されたフロントエンドファイルを確認する
2. Presentational / Container の分類を判断する
3. Presentational として実装されたコンポーネントに違反がないか照合する
4. 以下の形式で報告する

---

## Output Format

違反がある場合：

```
## Frontend Review 結果

### 違反あり
- **ファイル**: [ファイルパス:行番号]
- **違反内容**: 具体的な問題
- **修正方針**: 修正の方向性
```

違反がない場合：

```
## Frontend Review 結果

チェック完了。問題なし。
```

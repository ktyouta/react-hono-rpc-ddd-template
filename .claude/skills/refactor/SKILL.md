# Refactor Skill

## Overview

振る舞いを変えずに内部構造を改善する。

リファクタリングの鉄則：**テストが全通過するなら振る舞いは保たれている**。

---

## Steps

### Step 1: リファクタリング目的の把握

何を改善するか・なぜ改善するかを確認する。

```
## リファクタリング目的
- 対象: [ファイルパス]
- 現在の問題: ...
- 改善後の期待状態: ...
- 振る舞いへの影響: なし（振る舞いを変えないことを確認）
- 契約への影響: なし（事前条件・事後条件・不変条件を変えないことを確認）
```

---

### Step 2: 新規ファイル設計確認（新規ファイルがある場合のみ）

新規ファイルを作成する場合は、実装前に以下を提示してユーザーの承認を得る。

```
## 新規ファイル設計

| ファイルパス | 責務 | export するもの |
|---|---|---|
| ... | ... | ... |
```

承認を得てから次へ進む。新規ファイルがない場合はスキップする。

---

### Step 3: テスト通過確認（リファクタ前）

変更対象側のディレクトリ（`backend/` または `frontend/`）で `npx vitest run` を実行し、現在の全テストが通過していることを確認する（`npm run test` はウォッチモードで終了しないため使わない）。

テストが失敗している場合は、リファクタリングを開始しない（先に bug-fix で解消する）。

テストが起動段階で失敗した場合（例: `ConnectEx` 等で workerd が起動しない、`no tests`）は環境要因の可能性がある。変更前のコードでも同じ失敗が起きるかを確認してから判断し、「テスト通過」とは報告しない。

---

### Step 4: リファクタリング実施

Step 1 の目的に沿って内部構造を改善する。

ロジックを新規ファイルに移設する場合、対応するテストファイルの配置（ディレクトリ）も移設先に合わせて移動する（テスト内容自体は変更しない）。

既存テストの修正は、リファクタで変わった型・クラス名・import パスへの追従（例: `toBeInstanceOf(Entity)` → `toBeInstanceOf(ResultDto)`）のみ許可する。期待値（返す値・ステータスコード・件数など）の変更やテストケースの削除は行わない。修正した場合は完了報告にファイル名と理由を明記する。

参照リポジトリ等からファイルを取り込む場合は、取り込み後に `git diff` で差分を確認し、リファクタの目的（Step 1）や設計書（plan.md）にない変更（型・シグネチャ・命名の変更等）が含まれていないか照合する。含まれる場合は除外するか、plan.md の「実装時に Claude が判断したもの（未承認）」に記載してユーザーに確認する。

`schema.ts` を変更する場合（ユーザーが承認した場合のみ）は、db-migration スキルを実行し、その手順（生成 → SQL の確認 → 必要なら退避・戻しの追加 → 使い捨て D1 での検証 → ユーザーに断ってからローカルに適用 → 子孫テーブルを含む件数の報告）を完了する。あわせて Step 7 で db-naming-review を実行する。

---

### Step 5: テスト通過確認（リファクタ後）

`npx vitest run` を実行し、全テストが引き続き通過することを確認する。

テストが落ちた場合はリファクタリングを見直す（振る舞いが変わっている可能性がある）。

---

### Step 6: 型チェック・lint

テスト通過後、ルートで以下を実行してエラーが 0 件であることを確認する（変更範囲が backend だけでも両方実行する。frontend の型チェックはバックエンドの型定義を参照するため）。

- `npm run typecheck`（backend の tsc と、frontend の `tsc -b`。`tsc -b` はバックエンドの型定義 `backend/dist-types` を生成してから frontend の各 tsconfig をチェックする）
- `npm run lint`

`npx tsc --noEmit` を frontend で直接実行しない（`frontend/tsconfig.json` は references のみで、チェック対象を持たない）。

---

### Step 7: レビュー実行

以下のレビューを実行する：

- 変更がバックエンドなら backend-review
- 変更がフロントエンドなら frontend-review
- architecture-review
- comments-review
- performance-check
- バックエンドの RPC 型・レスポンス型・import パスを変更した場合は rpc-review
- `schema.ts` を変更した場合は db-naming-review

差分がファイルの移動と相対 import パスの変更のみの場合、comments-review と performance-check はスキップしてよい。スキップした場合は、その旨と理由（差分が import パスのみ）を報告に記載する。

---

### Step 8: session-retrospective 実行

全ステップ完了後に session-retrospective を実行する。

---

## Constraints

- 新規ファイルを作成する場合は Step 2 でファイル名・責務・export するものを提示し、ユーザーの承認を得てから実装に進む
- Step 3・5 のテスト確認、Step 6 の型チェック・lint は必ず実施する。省略しない。
- テストコマンドは `npx vitest run` を使う（`npm run test` は使わない）
- 既存テストの修正は型・名前・パスへの追従のみ。期待値は変更しない
- リファクタリング中に仕様変更・バグ修正を混入させない
- テストが落ちた状態で「振る舞いは変わっていない」と判断しない
- リファクタリングの範囲を指示の対象に限定する（スコープクリープしない）
- 契約（事前条件・事後条件・不変条件）を変えない。変える必要がある場合は refactor を中断し、feature-modify で扱う
- ドメイン層・`util/` に副作用・決定的でない処理を持ち込まない（CLAUDE.md の「クラス設計指針」）

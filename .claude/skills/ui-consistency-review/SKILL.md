# UI Consistency Review Skill

## Overview

UI 変更の前に画面全体を俯瞰し、個別対応によるデザイン崩壊を防ぐ。

「場当たり的な修正」を避けるため、変更前に以下の観点で全コンポーネントを評価する。
提案・修正方針の出力のみ行い、ファイルの変更はこのスキルでは行わない。

このスキルは「一貫性の確認」だけでなく「情報設計そのもの」も評価対象とする。
表・レイアウトをいきなり組む前に、まず「何を見せるべきか」を洗い出してから
一貫性・情報設計の両観点で評価する。設計とデザインを分けて考えない。

---

## Steps

### Step 1: 対象画面のコンポーネントを収集する

対象 feature の `components/` 配下のすべてのファイルを読む。

---

### Step 2: 一貫性チェック

以下の観点で全コンポーネントを横断的に確認する。

**カラーパレット**
- 使用されている色（Tailwind クラス・カスタム16進数）を列挙する
- 同種の要素に異なる色が使われていないか（例: テキストに `text-stone-500` と `text-gray-500` が混在）
- 背景色・ボーダー色・アクセントカラーが統一されているか

**スペーシングリズム**
- `mb-` / `mt-` / `gap-` / `px-` / `py-` の値を列挙する
- 隣接セクション間の余白が不規則でないか
- カードやボタンの内側余白（padding）が揃っているか

**タイポグラフィ階層**
- `text-*` / `font-*` の組み合わせを列挙する
- 見出し・ラベル・補助テキスト・エラーテキストの役割ごとに一貫したスタイルが使われているか

**視覚的重みのバランス**
- 各セクションの視覚的な存在感が意図通りの優先順位になっているか（主役・脇役・補助）
- 特定のコンポーネントが過剰・過小に主張していないか

**情報設計（要不要・強弱・見せ方）**
- 表示している情報のうち、ユーザーの意思決定に不要な項目が含まれていないか（Simple is BEST）
- 重要な情報と補助的な情報が同じ視覚的重みで並んでいないか（フォントサイズ・色・配置でメリハリがついているか）
- 生データをそのまま表示せず、ユーザー視点で加工されているか
  （例: タイムスタンプをそのまま出さず「3分前」と表示する、件数を棒グラフ的な表現にする 等）
- アイコン・色・配置などの装飾によって、説明文なしでも機能が直感的に伝わるか
  （例: 「編集」というラベルの代わりに鉛筆アイコンで表現できないか）

**インタラクションの統一感**
- hover / active / disabled の表現が統一されているか（`hover:opacity-80` と `hover:bg-xxx` の混在がないか）
- transition の有無・種類が揃っているか

---

### 修正提案の書き方（重要）

- 1つの提案は1〜2文の短い文で書く。長い1文に条件や理由を詰め込まない
- 専門用語（ハードコード・非選択状態 等）を使う場合は、その場で日常語に言い換える
  （例:「コードに直接書き込まれている」「まだ選んでいない方」）
- 「何が問題か」を一言で先に書き、次に「どうすればいいか」を書く。理由の説明は最後に付け足す程度にとどめる
- 前提知識のない人（中学生程度）が読んでも意味が伝わるかを基準にする

---

### Step 3: 評価を出力する

以下の形式で出力する。問題がなければ「問題なし」と出力して終了する。

```
## UI Consistency Review

### 現状の評価

#### カラーパレット
- 使用色: [一覧]
- 気になる点: [あれば記載、なければ「問題なし」]

#### スペーシングリズム
- 使用余白: [一覧]
- 気になる点: [あれば記載、なければ「問題なし」]

#### タイポグラフィ階層
- 使用スタイル: [一覧]
- 気になる点: [あれば記載、なければ「問題なし」]

#### 視覚的重みのバランス
- 気になる点: [あれば記載、なければ「問題なし」]

#### 情報設計
- 気になる点: [あれば記載、なければ「問題なし」]

#### インタラクション
- 気になる点: [あれば記載、なければ「問題なし」]

### 修正提案（優先度順）

1. [最優先: 最も影響範囲が大きい問題]
2. [次点]
3. [軽微]

→ 上記を踏まえた上で変更を進めます。
```

---

## Constraints

- ファイルの変更は行わない（評価・提案のみ）
- 一覧の列挙は省略しない（省略すると見落としが生じる）
- 「たぶん」「おそらく」ではなく、コード上で確認できた事実のみ記載する
- 提案は優先度順に並べ、最大5件に絞る
- 修正提案は平易な言葉で書く（専門用語の言い換え・一文一意を徹底する）

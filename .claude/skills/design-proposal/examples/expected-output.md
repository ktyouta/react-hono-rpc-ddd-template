# Expected Output — 設計案提示

## 入力例

「タスクの削除を論理削除にしたい。どう設計すればいい？」

---

## 期待される出力

```
## 設計案

### 案A: deleted_at カラムを追加する（ソフトデリート）

`tasks` テーブルに `deleted_at TIMESTAMP` カラムを追加し、
削除時に現在時刻をセット、復元時に NULL に戻す。

**メリット**
- 実装がシンプル
- 復元が容易（NULL に戻すだけ）
- 削除日時が記録される

**デメリット**
- 全クエリに `WHERE deleted_at IS NULL` の条件追加が必要
- 条件の書き忘れによるバグリスクがある

**実装コスト**: 低

---

### 案B: is_deleted フラグを追加する

`deleted_at` の代わりに `is_deleted BOOLEAN` を追加する。

**メリット**
- 意味が明示的でわかりやすい

**デメリット**
- 削除日時が記録できない
- 案Aと比べて情報量が少ない

**実装コスト**: 低

---

### 案C: 削除済みテーブルを分離する

`deleted_tasks` テーブルを別途作成し、削除時に移動・復元時に戻す。

**メリット**
- メインテーブルを汚染しない
- 削除済みデータのクエリが分離される

**デメリット**
- 実装が複雑（移動処理・外部キー整合性の管理）
- マイグレーションコストが高い

**実装コスト**: 高

---

## 推奨案: 案A（deleted_at カラム追加）

**理由**: 実装コストが最も低く、削除日時の記録・復元の両方に対応できる。
Drizzle ORM でのフィルタ条件追加も容易。

## 破綻するケース

- 削除済みデータを別のストレージ（アーカイブDB等）に移したい要件が出た場合、案Cへの移行コストが発生する
- 削除件数が膨大になりクエリパフォーマンスが問題になった場合、インデックス設計の見直しが必要になる
```

---

## 入力例（置き場所の相談）

「全コントローラーで同じ zod のエラーフック（型・構造の違反を固定のメッセージで返す処理）を、どこにまとめるべきか」

---

## 期待しない出力（NG）

```
## 推奨案: presentation/shared/error-message/ を新設する

**理由**: 固定のメッセージはどのコンテキストにも属さないため、共通ディレクトリに置く。
前例として middleware/ の errorHandler・notFoundHandler がある。
```

**NG の理由**:
- 既存の `middleware/` の中身を Read せずに、新しいディレクトリを作る案を出している
- `errorHandler`・`notFoundHandler` は `app.onError`・`app.notFound` で登録するハンドラーで、ミドルウェアではない。実体を確認せずに前例として挙げている
- 新しいディレクトリが既存のどこにも収まらない理由を示していない

---

## 期待する出力（OK）

```
## 設計案

### 案A: middleware/validator/ にミドルウェアとして置く

`zValidator` を固定のフックで包んだ関数を middleware/ に置く。

**根拠**
- `zValidator` は `MiddlewareHandler` を返す（`@hono/zod-validator` の型定義で確認）
- ルート単位で使い、失敗時に固定の応答を返すミドルウェアの前例として `authMiddleware`・`userOperationGuardMiddleware` がある（どちらもコントローラーのチェーンで使われている）

**メリット**
- フック全体（422・message・data の組み立て）を1か所にまとめられる

**デメリット**
- 包むと RPC の型推論が保たれるかを typecheck で確かめる必要がある

**実装コスト**: 低

---

### 案B: presentation/shared/ を新設し、メッセージを返す関数だけを置く

**メリット**
- メッセージの置き場所がプレゼンテーション層にそろう

**デメリット**
- 既存の middleware/ に収まる処理のために前例のないディレクトリを作る
- フックの重複（10か所）は残る

**実装コスト**: 低

---

## 推奨案: 案A（middleware/validator/）

**理由**: 処理の実体がルート単位のミドルウェアであり、既存の middleware/ に収まる。新しいディレクトリは不要。

## 破綻するケース

- 特定の API だけ型・構造の違反に別の応答を返したくなった場合、オプションの追加か素の zValidator への切り戻しが必要になる
```

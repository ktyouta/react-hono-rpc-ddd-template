# Feature Modify Skill

## Overview

既存機能の改修を、現状把握 → 影響範囲調査 → 差分設計 → 確認 → 実装 → レビュー → 仕様突き合わせ の順で一貫して進める。

feature-impl との違い：
- 既存コードを読んでから設計する（グリーンフィールドではない）
- horizontal-scope で影響ファイルを洗い出す
- 設計は「差分設計」（何が変わるか）を中心にする

---

## Steps

### Step 0: UI 変更の場合は ui-consistency-review を先に実行する

改修がフロントエンドの UI（コンポーネント・レイアウト・スタイル）を含む場合、Step 1 に進む前に ui-consistency-review を実行する。

以下をすべて含む（既存コンポーネントへの要素追加・削除もここに含まれる）：
- 新規コンポーネントの追加
- 既存コンポーネントへのボタン・入力・セクション等の追加・削除
- レイアウト・スタイルの変更

ui-consistency-review の結果を踏まえた上で、Step 1 の設計・実装に入る。

UI 変更を含まない場合はこの Step をスキップする。

---

### Step 1: 改修内容の把握

以下を確認する：

- 何を変えるか（変更前の動作・変更後の期待動作）
- なぜ変えるか（仕様変更・要望・問題解決）
- バックエンド / フロントエンド / 両方のどこに影響するか

---

### Step 2: 既存実装の確認

以下を読んで現状を把握する：

- `docs/[機能名]/plan.md`（設計書が存在する場合）
- 改修対象の既存コード（controller(Presentation) / usecase(Application) / repository・entity・VO(Domain/Infrastructure) / component / hooks）

**バグ修正を含む改修の場合は追加で以下を行う：**
- 問題が発生しているイベントフロー・データフロー・呼び出し経路を図示またはコメントで明示する
- 「どこで何が起きているか」を経路単位で追跡してから修正方針を決める
- 修正前に「この修正で経路上のどこが変わるか」を確認する
  - 曖昧なまま修正すると「直っていない」が複数サイクル発生する原因になる

---

### Step 3: horizontal-scope で影響範囲を洗い出す【必須・ブロッキング】

horizontal-scope を実行し、今回の変更パターンと同じ対応が必要なファイルを特定する。

**このステップを実行しない限り Step 4 に進んではならない。** Step 4 の差分設計テンプレートは「horizontal-scope 実行結果」を記載する欄を含んでおり、この欄は horizontal-scope を実際に実行しないと埋められない（「対応不要と判断したためスキップ」は理由にならない。対応不要という判断自体を horizontal-scope の実行結果として記載する）。

---

### Step 4: 差分設計を出力

変更前・変更後の差分を中心に設計をまとめる。

```
## 差分設計

### horizontal-scope 実行結果
- 対象ファイル: [一覧を列挙。他に対応が必要なファイルがない場合も「horizontal-scope 実行済み、追加対象なし」と明記する]

### 変更内容
- [変更前]: ...
- [変更後]: ...

### バックエンド変更点
- エンドポイント: ...
- Usecase メソッド: ...
- Repository メソッド: ...

### フロントエンド変更点
- コンポーネント: ...
- hooks: ...

### 変更・影響ファイル一覧

| ファイルパス | レイヤー | 操作 |
|---|---|---|
| ... | ... | 変更 / 新規 / 削除 |

### 仕様要件チェック（docs/[機能名]/spec.md 準拠）
docs/[機能名]/spec.md が存在する場合のみ実施する。

- spec.md から要件項目を抽出したか
- 全ての要件項目が差分設計（エンドポイント・Usecase・Repository・コンポーネント）に反映されているか

### フォルダ構成チェック（CLAUDE.md 準拠）
- エンドポイント単位のファイル分割になっているか
- バックエンドのファイルが1単位1フォルダ（`<名前>/<名前>.<種別>.ts` + `index.ts`）になっており、テストも同じフォルダに置かれているか
- `domain/{機能}/`（entity, value-object, repository interface）、`application/{機能}/`（usecase, dto）、`infrastructure/{機能}/repository/`、`presentation/{機能}/`（controller, schema）の4層構成に沿っているか
- repository に .interface.ts が `domain/` 側にセットで存在するか
- Container に -container.tsx サフィックスがついているか
- api/ に query-key.ts が含まれているか

### クラス仕様（契約）の変更
バックエンドの変更がある場合のみ記載する。変更するドメイン層（Entity・Value Object）・`util/`・Usecase について、契約（不変条件・事前条件・事後条件）の変更前・変更後を記載する。契約が変わらない場合も「契約の変更なし（理由: …）」と明記する（省略しない）。

| クラス・メソッド | 契約の種類 | 変更前 | 変更後 |
|---|---|---|---|

- **追加・更新するテストケース**: ...

### バックエンド設計チェック（CLAUDE.md 準拠）
バックエンドの変更がある場合のみ実施する。

- 変更するドメイン層・`util/`・Usecase の契約（クラス仕様）の変更点を記載したか
- ドメイン層・`util/` に副作用（外部状態の書き換え・I/O・ログ出力）を持ち込んでいないか。決定的でない処理（時刻・乱数・ID 生成）は名前付きファクトリメソッドに閉じ込めているか
- ドメイン層のクラスの書き方（不変性・`readonly`・生成方法など）を変える場合、backend-review の「契約・純粋性」の項目とぶつからないか確認したか。ぶつかる場合は差分設計の中で示し、項目の修正か設計の見直しかをユーザーに確認する
- Usecase の事後条件を、業務上意味のある分岐に限定しているか（Repository の呼び出し順などを契約にしていないか）

- Usecase は1エンドポイントにつき public メソッド `execute` 1つで、処理の流れと業務上の分岐を Usecase 内で完結させているか（Controller に処理の順序を組み立てさせていないか）
- 純粋なビジネスロジック（検証・計算）をドメイン層・`util/` に置き、Usecase は I/O と処理の流れの制御に徹しているか
- Controller が Repository・Drizzle に直接触れていないか
- 複数テーブル・複数モジュールへのアトミックな書き込みが必要な場合、1つの Repository メソッドに集約し `db.batch` を Infrastructure層内で完結させているか

問題がなければ実装に進みます。よろしいですか？
```

ユーザーの OK を得てから次へ進む。

OK を得たら、`docs/[機能名]/plan.md` が存在する場合は以下を更新してから Step 5 に進む：

- **決定事項**: この改修で決まった事項を追記する。ユーザーが自分で決めたものと、Claude の提案をユーザーが承認したものは分けて記載する（CLAUDE.md の「合意済み」表記ルールに従う）
- **未決定事項**: 今回決まった項目を未決定の一覧から削除する（一部だけ決まった場合は、残った範囲に書き換える）
- **タスク**: 差分設計で追加・変更・削除したタスクを反映する
- **クラス仕様（契約）**: 契約を変更した場合は「## クラス仕様（契約）」節を変更後の契約で更新する（節がなければ末尾に追加する）。spec-review の照合に使うため

plan.md と実態がずれると、feature-resume が再開ポイントを誤って判断する原因になる。

---

### Step 5: バックエンド変更実装

Step 4 の差分設計に沿ってバックエンドを変更する。

#### 【必須・ブロッキング】契約テストを先に追加・更新する（テスト駆動）

ドメイン層・`util/`・Usecase の契約を変更する場合は、Step 4 で記載した契約の変更に対応するテストを**コードの変更より先に**追加・更新する。以下の順で進める。

1. 変更後の契約に合わせてテストを追加・更新する（変更前の契約を検証しているテストは書き換え、残さない）
   - 書き換えずに残す既存テストについても、変更後の契約を全範囲で検証しているか確認する（例: 「自身を変更しない」を確認するなら、一部のフィールドではなくスナップショット全体を比べる）
2. `backend/` で `npx vitest run` を実行し、追加・更新したテストが**失敗することを確認する**（`npm run test` はウォッチモードで終了しないため使わない）
3. コードを変更し、テストを通す

テストの書き方：
- バックエンドのテストファイルは実装ファイルと同じ単位フォルダに配置する（例: `src/domain/sample/value-object/sample-name/sample-name.test.ts`）
- ドメイン層・`util/`：値を渡し、戻り値・保持する値・例外を確認する
- Usecase：Repository interface を満たすスタブ（オブジェクトリテラル + `vi.fn()`）を渡し、DB を使わずに戻り値と、業務上意味のある書き込みが行われた／行われなかったことを確認する
- 決定的でない値（ID・時刻）は具体値ではなく、存在・形式を確認する
- workerd の起動失敗（`ConnectEx` 等）で `no tests` になった場合は、テストの失敗・通過のどちらとしても扱わない（環境要因として報告する）

**失敗を確認していないテストでコードの変更に進まない。変更した契約の全項目にテストがあり、全件通過するまで Step 6 に進んではならない。**

その他の変更時の注意：

- `schema.ts` を変更した場合は db-migration スキルを実行し、その手順（生成 → SQL の確認 → 必要なら退避・戻しの追加 → 使い捨て D1 での検証 → ユーザーに断ってからローカルに適用 → 子孫テーブルを含む件数の報告）を完了する
- `drizzle/*.sql` を手で新規作成してはならない（生成された SQL への退避・戻しの追加は db-migration スキルの手順として許可する）
- ローカル D1 への適用を省略しない。`db:generate` はマイグレーションファイルの生成のみで DB 状態には反映されないため、適用を怠るとユーザーが実際に画面を開くまで SQL エラーが検出されない
- 参照リポジトリ等からファイルを取り込む場合は、取り込み後に `git diff` で差分を確認し、差分設計（plan.md）にない変更（型・シグネチャ・命名の変更等）が含まれていないか照合する。含まれる場合は除外するか、plan.md の「実装時に Claude が判断したもの（未承認）」に記載してユーザーに確認する

---

### Step 6: backend-review 実行

backend-review を実行する。あわせて resource-authz-review を実行する。

---

### Step 7: ユーザー確認（バックエンド）

**Step 8（フロントエンド実装）に進む前に必ず実施する。** DBマイグレーション適用（`db:generate`/`db:migrate:local`）の実行可否確認など、Step 5 の実装作業に付随する別の確認とは別物であり、それらの確認に紛れて省略してはならない。

以下の形式で出力し、ユーザーの確認を得る。

```
## バックエンド変更完了

### 変更ファイル
- [ファイルパス]: 変更の概要

### 実装内容サマリー
- エンドポイント: ...
- Usecase メソッド: ...
- Repository メソッド: ...

### 契約テスト結果
- 変更した契約項目: [n] 件 / 対応するテスト（追加・更新）: [n] 件
- 変更前の失敗確認: 済み（[n] 件失敗を確認）
- 実行結果: [n] 件中 [n] 件通過

### backend-review 結果
- 問題なし / 違反あり（詳細）

### resource-authz-review 結果
- 問題なし / 違反あり（詳細）

確認できたら実装を続けます。よろしいですか？
```

ユーザーの OK を得てから次へ進む。

---

### Step 8: フロントエンド変更実装

Step 4 の差分設計に沿ってフロントエンドを変更する。

変更に入る前に以下を必ず行う：

**8-a. Step 0 未実施チェック**

以下のいずれかに該当する場合は「UI 変更あり」と判定する：
- `<div>` / `<p>` / `<button>` / `<span>` 等の HTML 要素の追加・削除
- `className` のスタイルクラス変更（`items-*` / `gap-*` / `rounded-*` / `flex` 等）
- コンポーネントの追加・削除・入れ替え

「UI 変更あり」かつ Step 0 が未実施の場合、ui-consistency-review を今すぐ実行してから実装に進む。
バックエンド主体の改修でも差分設計後に JSX 変更が判明した場合はこのチェックが機能する。

**8-b. 対象画面の関連ファイルをすべて Read する**
- 対象画面のコンポーネント・ページファイルだけでなく、レイアウト・親コンテナも含む全ファイルを確認する
- 「雰囲気だけ把握した」ではなく「全ファイルを読んだ」状態で変更に入る
- クリッカブルカードなどのインタラクティブ要素を変更する場合、HTML 要素の選択（`div` vs `button` 等）も既存コンポーネントを Read して踏襲する

---

### Step 9: レビュー実行

以下を**全件実行**してから次へ進む（1つでも未実行の場合は Step を完了としない）：

- [ ] frontend-review
- [ ] architecture-review
- [ ] comments-review
- [ ] performance-check
- [ ] rpc-review（API 呼び出しを追加・変更した場合）
- [ ] db-naming-review（DB スキーマを変更した場合）

---

### Step 10: 仕様突き合わせ

以下のいずれかに該当する場合に spec-review を実行する。どちらにも該当しない場合はスキップする。

- `docs/[機能名]/spec.md` が存在する（Step 4 の仕様要件チェックと同じ判定基準）
- Step 4 でクラス仕様（契約）を変更した（spec.md の有無に関係なく実行し、Step 4 の「クラス仕様（契約）の変更」を照合の材料として渡す）

#### plan.md のタスク完了状況の更新

spec-review を実施したかどうかにかかわらず、`docs/[機能名]/plan.md` が存在する場合は、今回完了したタスクのチェックを `[x]` にする。

- 完了の判断は、実装とテストが通過していることを根拠にする（推測でチェックしない）
- Step 6・9 の NG が修正済みで、spec-review の「未実装」「仕様と異なる実装」が 0 件であることを確認してから `[x]` にする。未達の場合は `[x?]`（仮マーク）にとどめ、解消後に `[x]` に変える（feature-impl の Step 10 と同じ基準）
- 「コミット」のタスクはチェックしない（コミットはユーザーが行うため。未記載であれば `- [ ] コミット` を追加する）

---

### Step 11: NG 対応

Step 6（backend-review / resource-authz-review）・9・10 でいずれかの NG があった場合、skill-gap-detector を実行し、
既存 skill の漏れを特定して修正提案を行う。

---

### Step 12: session-retrospective 実行

全ステップ完了後に session-retrospective を実行する。

## Constraints

- 各 Step は順番通りに実行する（並行実行しない）
- Step 3（horizontal-scope）は省略しない。Step 4 の差分設計に「horizontal-scope 実行結果」欄を必ず含める（対応不要と判断した場合もその旨を明記する。無言でスキップしない）
- ユーザー確認（Step 4・7）では必ずユーザーの明示的な OK を得てから次に進む。Step 7 はマイグレーション適用可否など他の確認作業と混同して省略しない
- `docs/[機能名]/plan.md` が存在する場合、Step 4 の承認後（決定事項・未決定事項・タスク・契約）と Step 10 の後（タスクの完了状況）に必ず更新する
- 既存テストが存在する場合は、変更後も通過するか確認する
- バックエンド・フロントエンドの実装完了後は、ルートで `npm run typecheck` と `npm run lint` を実行し、エラーが 0 件であることを確認する
- 契約を変更する場合、テストをコードの変更より先に追加・更新し、失敗を確認してからコードを変更する
- 契約（クラス仕様）の変更点に対応するテストがない状態、またはテストが通過していない状態で backend-review に進まない
- 指示にない機能を変更に追加しない
- エラーや NG を無視して次のステップに進まない
- schema.ts を変更した場合は必ず db-migration スキルの手順に従う。`drizzle/*.sql` を手で新規作成しない
- schema.ts を変更した場合は、db-migration スキルの検証を通してから、ユーザーに断って `db:migrate:local` でローカル D1 に反映する
- コーディング規約・チェック項目の追加は skill ファイルにのみ行う。skill で対応できる内容を CLAUDE.md に追記しない
